# M1.3A thermal V3 rebuild test

This is a seven-object experiment using audited Level1 object/component IDs. It is not a full Level1 importer. `tools/prepare-m13a-thermal.py` derives `Levels/Drafts/M1.3A/thermal-baseline.v3.test.json` and `thermal-edited.v3.test.json` from the unchanged M1.2 Level1 draft. The only differences are Ice step 2 local X `0 → 0.75` and its BoxCollider2D height `1 → 1.25`. The source Scene, M1.2 draft, source YAML backup, component IDs, and references remain untouched. `field-coverage.json` lists each mapped source field and each preserved-only field.

## Data authority

- `ObjectV3.localPosition`, `localRotation`, `localScale`, and mapped `ComponentV3.data` drive creation of new Unity objects. The importer never applies `sourceSerialized.fields` or `rawYaml` after typed values. The second binding pass reads typed `linkedController`, ordered `controlledIce`, and `roomFilterOverlay` references using exact component IDs.
- `sourceSerialized` is an immutable, SHA-256 checked backup of the original Unity component document. It remains available for later adapter work. A field absent from the M1.3A mapper is listed as preserved-only in `field-coverage.json`; it is **not** claimed to affect the new Unity scene.
- `dataStatus: m13aMapped` is limited to Transform, SpriteRenderer, BoxCollider2D, BaseBlock, IceBlock and ThermalControllerBlock for this exact test fixture. The TS validator and Unity importer reject unknown typed fields, missing components, invalid target IDs/types, unsupported materials, and changed source document hashes.
- Unity's existing IceBlock logic owns the effective SpriteRenderer color and Collider enabled state after the initial temperature is applied. A typed SpriteRenderer source color can therefore differ from the effective ice color at runtime. This is an explicit runtime-state effect, not YAML replay.

## Unity isolation and menu

The Editor code requires the existing `Phase4A.IsolatedProject.marker`, exact test Company/Product values, an unchanged isolated `Level1.unity` SHA-256, and a clean active scene. It creates a unique `Assets/Scenes/LevelEditorM13A_Thermal_<GUID>.unity` inside the isolated project only. A generated scene is never mistaken for the official Level1. Any failure logs the generated path so an incomplete scene is not used as a PASS.

After syncing only the new M1.3A scripts, their `.meta` files, the two test JSON files, and `Level1.source.json` into the isolated Unity project, use:

1. **Physics Level Editor → M1.3A → Prepare isolated V3 thermal data rebuild**. Wait for `M13A_ISOLATION_PASS`, then `M13A_DATA_STATUS=PASS; ... editedIce2X=0.75; editedColliderY=1.25; refs=PASS`. `M13A_PLAY_STATUS=NOT_RUN` is expected.
2. **Physics Level Editor → M1.3A → Prepare and play isolated V3 thermal mechanics**. It creates another unique test scene, checks saved/reopened data, and enters Play Mode. `M13A_PLAY_STATUS=NOT_RUN; entering Play Mode` is a preparation message. Only the runtime probe may emit `M13A_PLAY_STATUS=PASS` after hot→cold→hot toggles, four Collider checks, ordered reference checks, the edited Transform/Collider checks, and an error-log check. Any failure emits `M13A_PLAY_STATUS=FAIL`.

The probe does not require a player or SaveManager; the isolated Company/Product also differs from the formal game's persistent-data identity. Do not claim a Play PASS until the actual probe log appears in a Unity Editor run.

## Verification limits

`npm.cmd run check`, `npm.cmd run build`, and `python tools/compile-m13a-static.py` are static/data checks. The C# compiler script uses installed Unity assemblies and cached isolated-project game assemblies; it cannot replace Editor script import or Play Mode. The old V1/V2 adapters, gameplay scripts, formal Scenes, and ProjectSettings are unchanged. M1.3B must expand component coverage and verify how preserved-only Unity fields affect reconstruction before general V3 editing is enabled.
